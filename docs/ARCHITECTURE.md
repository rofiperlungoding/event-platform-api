# Architecture

This document describes the architectural decisions, trade-offs, and
operational patterns that define the Event Platform API. It is intended
for developers maintaining or extending the system.

---

## Principles

1. **Operational simplicity over feature completeness.** Each component
   has one well-defined responsibility. The cost of additional features
   is measured in operational complexity, not lines of code.

2. **Fail closed, recover automatically.** Every component is paired with
   detection and recovery: smoke tests gate deployment, watchdog cron
   restarts hung processes, rollback restores known-good binaries.

3. **Client-side intelligence.** The frontend (a Progressive Web App)
   absorbs request bursts via offline queueing. The server processes a
   sustained load rather than a spike.

4. **No vendor lock-in beyond TLS termination.** All persistent state
   lives on the host. Cloudflare provides only ingress; replacing it
   requires only a new public IP and a reverse proxy.

## Data Model

```
Participant ──┬─── Attendance ─── Session
              │
              └─── Device
```

### `Participant`

| Field            | Type      | Notes                                |
| ---------------- | --------- | ------------------------------------ |
| `id`             | SERIAL    | Primary key                          |
| `name`           | VARCHAR   | Display name                         |
| `email`          | VARCHAR   | Unique identifier for login          |
| `team`           | VARCHAR   | Logical grouping                     |
| `password_hash`  | VARCHAR   | Currently plaintext (see roadmap)    |
| `role`           | VARCHAR   | `'participant'` \| `'admin'`         |
| `createdAt`      | TIMESTAMP | Defaulted to `NOW()`                 |
| `updatedAt`      | TIMESTAMP | Defaulted to `NOW()`                 |

### `Session`

A time-bound attendance window identified by an opaque short code.
Codes rotate every 30 seconds (driven by the admin frontend) to prevent
QR code screenshot abuse.

| Field         | Type      | Notes                                          |
| ------------- | --------- | ---------------------------------------------- |
| `id`          | SERIAL    | Primary key                                    |
| `code`        | VARCHAR   | 8-character alphanumeric, unique               |
| `created_by`  | INTEGER   | FK to `Participant.id`                         |
| `expires_at`  | TIMESTAMP | Default: 30 minutes after creation             |
| `active`      | BOOLEAN   | Set to `false` when admin stops the session    |

### `Attendance`

A single check-in event. The composite uniqueness constraint
`(participant_id, session_id)` prevents double-counting.

| Field            | Type      | Notes                              |
| ---------------- | --------- | ---------------------------------- |
| `id`             | SERIAL    | Primary key                        |
| `participant_id` | INTEGER   | FK to `Participant.id`             |
| `session_id`     | INTEGER   | FK to `Session.id`                 |
| `device_id`      | VARCHAR   | The device that performed check-in |
| `checkedInAt`    | TIMESTAMP | Server-assigned at insert          |

### `Device`

Maps anonymous device UUIDs (generated by the PWA) to `Participant`
identities. This enables QR scans to identify the participant without
requiring an explicit login on every check-in.

| Field            | Type      | Notes                                          |
| ---------------- | --------- | ---------------------------------------------- |
| `device_uuid`    | VARCHAR   | Generated client-side via `crypto.randomUUID()` |
| `participant_id` | INTEGER   | FK to `Participant.id`                         |
| `user_agent`     | TEXT      | Recorded for forensic purposes                 |
| `linkedAt`       | TIMESTAMP | Last linkage timestamp                         |

## Request Lifecycle

### Standard API Request

```
1. Client sends HTTP request to api.example.com
2. Cloudflare edge terminates TLS, routes via QUIC tunnel
3. cloudflared on tablet receives request, proxies to localhost:3001
4. event-server accepts the connection
5. event-server reads up to 64 KB of headers + body
6. Request is parsed (method, path, headers, body)
7. Router dispatches to handler
8. Handler:
   - Optionally verifies bearer token via verify_token()
   - Opens a per-request PostgreSQL connection
   - Executes parameterised query
   - Builds JSON response into a growable strbuf
   - Writes response with CORS headers
   - Closes the database connection
9. event-server closes the client connection (SO_LINGER=0 → RST)
10. cloudflared returns the response upstream
```

### Webhook Deployment Request

```
1. GitHub fires push webhook
2. event-server validates ?secret= query parameter
3. event-server forks a detached child process
4. Child process:
   - Detaches from controlling terminal (setsid)
   - Resets SIGCHLD handler (parent has SIG_IGN)
   - Redirects stdio to /dev/null
   - execl(bash, deploy-api.sh)
5. Parent immediately responds 202 Accepted
6. deploy-api.sh:
   a. git fetch + reset --hard origin/main
   b. cc compile to event-server-staging
   c. Run staging on port 3099
   d. curl -sf http://localhost:3099/health
   e. On failure: log + exit (current binary untouched)
   f. On success: archive current, atomic mv staging → production,
      pm2 restart event-server
7. Final health check on the production port
```

## Authentication

The token format is a deliberately simple non-cryptographic scheme suitable
for educational and low-stakes environments:

```
<participant_id>:<expiry_unix>:<role>:<fnv1a_hex_signature>
```

Where the signature is computed over `<id>:<expiry>:<JWT_SECRET>` using
FNV-1a 64-bit hashing.

### Verification Procedure

1. Parse the four colon-separated fields.
2. Reject if `expiry < now()`.
3. Recompute the signature locally.
4. Reject if the recomputed signature differs from the supplied one.
5. Return `participant_id` and write the role to the caller's buffer.

### Limitations

- FNV-1a is **not cryptographic** — it is fast and convenient, but a
  motivated attacker with sufficient observed tokens could potentially
  reconstruct the secret. For production use, replace with HMAC-SHA256.
- There is no token revocation list. A leaked token is valid until
  `expiry`. Mitigated by short token lifetimes (24 hours).

## Concurrency Model

The server uses a **single-threaded blocking accept loop**. There is no
worker pool, thread, or event loop. Each connection is processed
sequentially.

### Justification

This was a deliberate reversal of an earlier `fork()`-per-request prefork
design that produced two distinct failure modes on Termux:

1. **Orphaned worker children** held the listen socket after pm2 restarts,
   producing `bind: Address already in use` until the entire Termux app
   was force-stopped.
2. **Phantom port locks** — children whose parent had already exited
   could not be located via `ps`, `lsof`, or `netstat` due to Android's
   process visibility restrictions.

The single-threaded model trades raw throughput for operational
predictability. Combined with the offline-first PWA client (which queues
and replays requests during connectivity gaps), this provides sufficient
throughput for the target workload.

### Capacity Envelope

| Path                          | Sustained throughput |
| ----------------------------- | -------------------- |
| Direct LAN (no tunnel)        | ~140 req/s           |
| Through Cloudflare Tunnel     | ~45 req/s            |
| With offline-first PWA buffer | Effectively unbounded for bursts; limited only by sustained 45 req/s |

For a 2,000-participant event with check-ins concentrated in a 60-second
window, the PWA queues locally and replays at the sustained rate over
~45 seconds. No participant experiences a perceptible delay.

## Stability Architecture

The system implements four prevention layers and three fallback layers
to mitigate deployment risk.

### Prevention

1. **No prefork.** Eliminates orphan-children class of bugs.
2. **`SO_LINGER` with timeout 0.** Forces RST on close, releasing the
   port immediately and avoiding the 60-second TIME_WAIT lock.
3. **Smoke test before swap.** A new binary is exercised on a test port
   before replacing the production binary.
4. **pm2 max-restart limit (5).** Bounded crash-loop tolerance prevents
   infinite restart cycles consuming CPU.

### Fallback

1. **Binary archive.** Each successful deploy archives the prior binary
   to `~/projects/event-server-archive/`. The most recent five are
   retained.
2. **Health watchdog.** A cron job runs every five minutes. If the API
   is unhealthy, it issues `pm2 restart`. If still unhealthy, it
   triggers automatic rollback.
3. **Manual rollback.** A webhook endpoint can restore the most recent
   archive on demand: `POST /deploy/run/rollback?secret=...`.

### Maximum Time to Recovery

| Failure mode                              | MTTR      |
| ----------------------------------------- | --------- |
| Process crash without code change         | < 1 sec   |
| Bad deploy, smoke test catches it         | 0 sec (production never updated) |
| Bad deploy that passes smoke but fails in production | ≤ 5 min (watchdog detection + rollback) |
| Tablet reboot                             | ~ 30 sec  |
| Tunnel disconnection                      | Auto-recovered by cloudflared    |
| Database corruption                       | Manual restore from `~/backups/` (≤ 24 hour data loss) |

## Frontend Architecture

The frontend is a static-only PWA, served from the same C server as the
API. Critical patterns:

### Offline-First Check-In

When a participant scans a QR code:

1. The scanner attempts `POST /attendance/checkin`.
2. On network error, the request is enqueued in IndexedDB.
3. A Service Worker registers a Background Sync (`sync-checkins`).
4. When connectivity is restored, the Service Worker drains the queue.
5. The user sees an immediate "checked in (pending sync)" confirmation;
   the green-dot indicator transitions to synced once the server confirms.

### Device-Bound Identity

On first launch, the PWA generates a UUID and persists it in
`localStorage`. After successful login, the UUID is bound to the user
via `POST /device/link`. Subsequent visits identify the user via
`POST /device/identify` without requiring a password.

This pattern enables fast check-in flows: scan QR, immediate post,
no login screen.

## Deployment Topology

### Single-Tablet Reference

The reference deployment runs all components on a single Android tablet:

- One `event-server` process
- One `event-tunnel` (cloudflared) process
- One PostgreSQL instance
- One cron daemon

This topology is suitable for events of up to ~2,000 participants when
paired with the offline-first PWA. It is **not** suitable for:

- Multi-tenant SaaS deployments
- Workloads requiring sustained > 50 req/s
- Compliance-regulated data (HIPAA, PCI, etc.)

### Multi-Host Extension (Future)

For larger deployments, the system can be extended:

- Move PostgreSQL to a dedicated host or managed service.
- Run multiple `event-server` instances behind a load balancer (e.g.,
  Nginx, Cloudflare Load Balancing).
- Replace the Cloudflare quick-tunnel with a named tunnel or static
  public IP.

The C server is stateless (per-request DB connection); horizontal
scaling requires no application changes beyond externalising the
configuration.
